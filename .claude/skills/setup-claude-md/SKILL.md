# /setup-claude-md — interview your way to an effective CLAUDE.md

Produce a CLAUDE.md that earns its context cost. Source of truth for what "effective" means: https://code.claude.com/docs/en/best-practices#write-an-effective-claude-md — the rules below are distilled from it.

**The one test for every line:** *"Would removing this cause Claude to make mistakes?"* If not, it doesn't go in. A bloated CLAUDE.md causes real instructions to be ignored — length is not thoroughness, it's dilution.

## What belongs (from the official table)

| ✅ Include | ❌ Exclude |
|---|---|
| Bash commands Claude can't guess | Anything Claude can figure out by reading code |
| Code style rules that differ from defaults | Standard language conventions Claude already knows |
| Testing instructions and preferred test runners | Detailed API documentation (link to docs instead) |
| Repository etiquette (branch naming, PR conventions) | Information that changes frequently |
| Architectural decisions specific to the project | Long explanations or tutorials |
| Developer environment quirks (required env vars) | File-by-file descriptions of the codebase |
| Common gotchas and non-obvious behaviors | Self-evident practices like "write clean code" |

Two placement rules on top of that:

- **Machine-local facts don't go in CLAUDE.md at all.** Absolute paths, install locations, and machine-verified commands go in a gitignored `LOCAL.md`, imported via `@LOCAL.md`. CLAUDE.md references keys like `<UnrealProjectDir>`. If LOCAL.md is missing or incomplete, run `/setup-local-md` (the dedicated interview for those variables) rather than collecting them here.
- **Sometimes-needed procedures don't go in CLAUDE.md either** — CLAUDE.md loads every session. A workflow only used occasionally belongs in a skill; suggest that split when you see one.

## Entries this scaffold needs to function

Everything else in this skill is about judgement. This part isn't: the agents, skills and hooks shipped here read specific things out of CLAUDE.md, and they degrade quietly when those are missing — an agent doesn't announce that `<UnrealProjectDir>` failed to resolve, it just improvises. Carry these into any CLAUDE.md you write for a workspace using this scaffold, filling the values from the interview.

**Always required:**

1. **`@LOCAL.md` import**, on its own line. Every skill and agent refers to machine paths as `<UnrealProjectDir>`, `<UnrealEngineDir>`, `<BuildScript>`, `<Python3>`. Those keys resolve only because LOCAL.md is imported. Without it every such reference is dead text.
2. **The build command and its preconditions.** `builder`, `/tdd`, `/release-gate` and `/unlock-unreal` all shell out to it. For Unreal, state that the editor must be **closed** — Live Coding blocks UnrealBuildTool, and this is the single most common way a build fails for a reason nobody understands.
3. **The test command, what a pass looks like, and what noise to ignore.** `/tdd` and `reviewer` verify by running tests and reading output. "Tests pass" is not a checkable claim without the exact success signature.
4. **Pointers to the convention docs** — asset naming and folder structure. `architect`, `builder` and `reviewer` all read them, and the review pre-pass script *parses* the naming doc for its prefix table. If that file is missing or renamed, the asset-naming check silently skips.
5. **A note that `.claude/skills/` stays flat.** Grouping skills into category subfolders silently unregisters every skill inside them. It looks tidy and breaks everything, so it is worth one line.

**Required when the workspace drives a live editor over MCP:**

6. **What to do when MCP drops.** C++ builds close the editor, which kills the MCP server. Record that the fix is self-serve — relaunch, make a call or two, let the harness re-attach — so agents don't stall waiting for a human. Ending up blocked on a human for something the agent can do itself is a real cost.
7. **The VibeUE agent guide import** (`@<UnrealProjectDir>\CLAUDE.md`), if VibeUE is installed. It documents the plugin's own tools and is regenerated by a console command after plugin updates.
8. **The live-testing playbook pointer**, if the workspace drives play sessions. Several of its entries correct approaches that look right and produce confidently wrong results.

**Strongly recommended:**

9. **Canonical documentation URLs** for the engine and its scripting API. Invented APIs are a recurring failure mode, and a URL in CLAUDE.md is what turns "I think this method exists" into a check.
10. **The agent and skill inventory, with model pins and the file-ownership table.** The main session dispatches from this; pinning models explicitly means a `/model` switch doesn't silently change what tier the agents run at.

Fill these from the interview rather than pasting another project's values — a build command copied from a different machine is worse than none, because it looks verified.

## Process

### 1. Explore before asking

Read the existing CLAUDE.md (note every `[FILL IN]` and stale-looking claim), the repo layout, build/config files, and git history. **Never ask the user something the repo can answer** — the interview is for facts that aren't derivable: which commands are actually used, unwritten conventions, decisions already made, what's deliberately out of scope.

### 2. Interview — one question at a time, with a recommendation

Ask one question per turn, each carrying your recommended answer so the user can confirm or redirect cheaply (use `AskUserQuestion` if available). Cover, in roughly this order, skipping whatever exploration already answered:

1. **Build** — the exact command that compiles the project, and any preconditions (e.g. "editor must be closed"). If you can run it safely, verify it before recording it as verified — a wrong command in CLAUDE.md is worse than none.
2. **Test** — the exact command, what a pass looks like, what noise to ignore.
3. **Layout** — where new code goes; which directories are owned by what. One paragraph, not a tree dump.
4. **Conventions that differ from defaults** — naming rules, forbidden libraries, patterns deliberately not used.
5. **Gotchas** — the things a competent newcomer would get wrong. These are the highest-value lines in the file; push for at least the top two ("what bit you last month?").
6. **Workflow rules** — commit/branch etiquette, what needs human approval, phase gates.
7. **Project context** — status, ownership split, decisions already made (link the doc that records them rather than restating it).

Stop interviewing when the remaining questions would produce ❌-column content.

### 2b. Working style — how this person wants to be worked with

Everything above is about the project. This part is about the human, and it is worth real effort: it changes every exchange, not just the ones that touch a build command.

**Mine corrections before asking anything.** People are unreliable narrators of their own preferences and very reliable reactors to violations of them, so observed behaviour beats self-report. Scan the conversation, recent commits and any existing notes for places the user said "no, do X instead", reverted something, or repeated an instruction. **A behaviour corrected twice is a style rule** — write it down and confirm it rather than asking cold. The strongest lines in a mature CLAUDE.md usually got there this way; a rule like "never claim a test passed without running it" reads like it was written the day something got fabricated, and it is worth more than any interview answer.

**Then ask about behaviour in specific situations, never about abstract preferences.** "Do you want clear communication?" gets a yes from everyone and produces a dead line. These six discriminate:

1. **"I hit a fork with two reasonable options and no clear winner — pick the better one and keep going, or stop and ask?"** Sets the autonomy level. The highest-leverage answer here, and it varies enormously between people.
2. **"I think your approach is wrong. Say it once and comply, or argue until one of us is convinced?"** Most people want push-back and few say how much.
3. **"What makes you believe a claim — the reasoning, a passing test, a screenshot, or seeing it run?"** Whatever they answer becomes the standard of evidence for "done".
4. **"What behaviour from an assistant makes you want to stop using it?"** The most discriminating question on the list. Negative examples are far sharper than positive ones, because everyone endorses the positives.
5. **"What do you tend to overdo? What do people push back on you about?"** Uncomfortable, which is exactly why it produces something real — and it yields the most useful block of all, a short list of the user's own failure modes to counter.
6. **"When you're the bottleneck — an unreviewed change, a decision I'm waiting on — should I say so, or wait quietly?"** Some people want to be told immediately; others find it presumptuous. Both are legitimate and you cannot guess which.

If the user offers a personality type or profile, treat it as a **hypothesis to verify, not a fact to record.** "The maintainer is an ENTJ" is not actionable — nothing I do on Tuesday changes because of it. The derived behaviour is: *lead with the recommendation, they will ask for detail if they want it.* Record the behaviour and drop the label. Where the profile and the observed corrections disagree, the corrections win.

**Write it as instructions, not as a description of the person.** Compare "the maintainer is decisive and hates hand-holding" — which tells me nothing to do — with "when a fork has an obvious better option, take it and say which you took." The second changes behaviour; the first is a horoscope.

**Cap it at roughly 10–15 lines.** Style content competes for the same always-loaded budget as build commands, and the removal test still applies: if the assistant already does it by default, cut it. Restating default behaviour trains the reader that rules in this file are optional, which quietly weakens the rules that matter.

### 3. Draft, prune, confirm

Write the draft, then make a second pass applying the removal test line by line — cut what survives only because it sounds professional. Keep it short and human-readable; there is no required format. Emphasis ("IMPORTANT", "YOU MUST") is a scarce resource — spend it on at most the one or two rules where violation is expensive.

Show the user the draft (or a diff against the existing file) and get a yes **before writing** CLAUDE.md — it's the most load-bearing file in the repo. Then write it, plus LOCAL.md / LOCAL.md.example / the `.gitignore` line if they were part of the change.

### 4. Close the loop

Tell the user: run `/context` in a fresh session to confirm the file loads, and treat CLAUDE.md like code from here on — when Claude repeatedly gets something wrong, the fix is usually pruning the file or sharpening one rule, not adding a paragraph. If a rule must hold with zero exceptions, recommend a hook instead (hooks are deterministic; CLAUDE.md is advisory).
